# dingxiang — Dingxiang (顶象) slider captcha solver

Pure-HTTP solver for the Dingxiang v5 web slider (`captcha-ui` SDK). The wire
protocol was reconstructed by **live capture of the official demo page**
(`cdn.dingxiang-inc.com/ctu-group/captcha-ui/demo/`, SDK v5.1.53, 2026-09-13)
and cross-checked against the param model published by
[aidencaptcha/DingxiangCaptchaBreak](https://github.com/aidencaptcha/DingxiangCaptchaBreak)
(Apache-2.0) — the reference repo documents the `ak / appKey / greenseer / ac /
token` param family but ships no source; its algorithm is closed-source.

## Protocol (live-captured, v5 web)

```
1. GET  https://cap.dingxiang-inc.com/api/a
        ?w=300&h=165&s=50&ak=<appId>&c=<constId>&jsv=5.1.53
        &aid=dx-<ms>-<rand>-<seq>&wp=1&de=0&uid=&lf=0&tpc=&cid=<8digits>&_r=<rand>
   → {"sid": "<32hex>", "cid": ..., "y": <gap Y, native px>, "type": 0,
      "p1": "/dx/<...>.webp", "p2": "/dx/<...>.webp", ...}
   sid  = challenge session id (widget-stable, reused across refreshes)
   y    = server-provided gap Y (native image px, canvas-anchor row)
   p1   = background image (observed native 400x200), p2 = RGBA piece (68x68)

2. GET  https://static4.dingxiang-inc.com/picture<p1>   (and <p2>)

3. POST https://cap.dingxiang-inc.com/api/v1   (x-www-form-urlencoded)
        ac=<SDK encrypted blob>&ak=<appId>&c=&uid=&jsv=5.1.53&sid=<sid>
        &aid=<aid>&x=<piece final left offset, box px>&y=<gap Y>&w=300&h=165&cid=<cid>
   → {"success": bool, "token": str|null, "msg": "retry"|..., "retry": int}
```

Optional constId (device id, raises pass rate):
`GET https://constid.dingxiang-inc.com/udid/c1?_t=<ms5>` →
`{"data": "<constId>", "status": 1}` — the constId is then sent as `c=` in
step 1 (observed: first request empty, later requests carry it).

### Coordinate semantics (verified with controlled drags)

- `x` = final **left offset of the slider piece inside the image box**, i.e.
  `piece_rest_offset (20 px) + drag distance`, in **box pixels** (`w` param).
  Verified live: a 120 px drag produced `x=140`; a drag to piece offset 63.75
  produced `x=63` (SDK truncates). Images are served larger than the box
  (400x200 native vs 300x165 box) → native→box scale `w / bg_native_w`.
- `y` = echoed back unchanged; the widget places the piece top at this row.

## Param table (reference glossary → wire mapping)

| Param (reference) | Meaning | Where it appears here |
| ----------------- | ------- | --------------------- |
| `ak`              | 32-hex public captcha appId, per-scenario | `ak=` in `/api/a` and `/api/v1` (`app_id`) |
| `appKey`          | per-scenario secret key | never sent to the wire; forwarded to ac providers in the ac ctx |
| `greenseer`       | encrypted telemetry/risk payload family generated by the obfuscated SDK | the `ac` form field of `/api/v1` (closed-source — see boundary) |
| `ac`              | signed/encrypted request checksum+blob | `ac=` in `/api/v1` |
| `token`           | final pass token returned on success | `token` in the `/api/v1` response (result `token`); downstream sites verify it as `ticket=<token>:<suffix>` with a `constID=CID:<ms>` param (see the reference vivo example) |
| `sid`             | challenge session id | `/api/a` response → `/api/v1` field |
| `aid` / `cid`     | widget instance id / per-page client id | generated (`dx-<ms>-<rand>-<seq>` / 8 digits) |

## Flow (`solve_dingxiang`)

1. `app_id` resolution: argument → `extract_app_id()` on `url`'s HTML →
   official public demo appId (test target).
2. Optional constId (`constid=True`).
3. `GET /api/a` → `sid`, `y`, `p1`, `p2` (rejects non-slider `type`).
4. Download images from the picture CDN.
5. `detect_gap()` — gap X via masked Pearson correlation of the piece's RGB
   content against each background window (affine-invariant to the hole
   darkening), alpha mask eroded to drop the piece's baked-in white outline,
   search pinned to the server row band. Background size is read to convert
   native → box coordinates.
6. `generate_trajectory()` — deterministic human-shaped drag (fast start,
   decelerate, 3-7% overshoot, multi-step correction, micro-pauses).
7. `ac` resolution, then `POST /api/v1`; `msg:"retry"` → fresh challenge and
   retry (`max_attempts`), anything else fails fast.

### ac (greenseer) sources — the honest capability boundary

The `ac` blob is the SDK's encrypted trajectory/environment payload. Its
encryption lives in the XOR-obfuscated v5 SDK and is **not implemented here**
(it is exactly what the reference repo's authors sell as a service). Three
supported sources:

| Source | Usage |
| ------ | ----- |
| `ac="5903#..."` | use a pre-captured/provider blob as-is |
| `ac=callable(ctx)` | generate per-attempt from `{sid, ak, app_key, x, y, w, h, distance, trajectory, referer, aid, cid, jsv}` |
| `ac_api="http://provider/ac"` | POST the same ctx JSON, expect `{"ac": "..."}` back |

Without either, the solver runs **challenge-only**: it performs steps 1-6 and
returns `solved:false` with `error` explaining the missing ac, plus a ready
`submit_payload` (all `/api/v1` fields except `ac`) and the `distance` /
trajectory — for callers that complete the submission with their own ac
generator.

Live-status note (2026-09-13): submissions on the official demo with
SDK-generated ac blobs (real pointer drags in Chromium, correct box-space
geometry `x=89` for a server `y=42` challenge) still returned `msg:"retry"`,
so beyond the position the server also enforces trajectory/environment risk
checks inside `ac`. Treat guaranteed end-to-end solving as requiring a working
ac/greenseer provider; everything else in the pipeline is pure-HTTP and
provider-agnostic.

### Gap detection — validation evidence

- Reference fixture (`fixtures/example_bg.png` + `example_piece.png`, from the
  DingxiangCaptchaBreak example annotated `distance.(268, 49)`): detected
  **(268, 49)** exactly, Pearson score 0.965.
- Synthetic pair (programmatic darkened-content hole, canvas margin): exact
  hit, score 0.9996.
- Live v5 webp challenges: hole styling is subtle and varies; the detector
  converges (typical score 0.2-0.5) but per-challenge accuracy is **not
  server-verified** (see boundary above). Tuning hooks: `erode_px`,
  `y_slack`, `exclude_rest_px`.

Run `selftest.py` for the full offline check suite (30 assertions, no
network needed for the URL/trajectory parts; fixture test auto-skips if
fixtures are absent).

## Request / Response

```json
POST /solve
{
  "type": "dingxiang",
  "app_id": "12610a3853150e888ccd0c6d4c415626",  // optional → demo default
  "url": "https://target/page",                  // optional → Referer + appId scan
  "app_key": "...",                              // optional → forwarded to ac provider
  "ac_api": "http://127.0.0.1:9000/ac",          // optional ac provider
  "proxy": "http://user:pass@host:port",         // optional (socks via curl_cffi)
  "timeout_s": 90
}
```

```json
{
  "solved": true,
  "type": "dingxiang",
  "token": "9fbf8b52c9d0c33cb8dd7ba6dcf1eb57",   // pass token for the site's verify call
  "method": "pure-http-slider",
  "elapsed": 6.2,
  "error": null,
  "app_id": "12610a3853150e888ccd0c6d4c415626",
  "sid": "f4b2d39d5730d7a30164fcd2f35a71bd",
  "gap_x": 247, "gap_y_server": 70, "gap_score": 0.31,
  "gap_x_display": 185.25, "bg_native_size": [400, 200],
  "distance": 165.25, "trajectory_points": 32,
  "attempts": 1, "submit_msg": null
}
```

Challenge-only failure keeps the contract: `solved:false`, `error` set,
`mode:"challenge-only"`, `submit_payload` filled.

## Dependencies

`httpx` (socks proxies fall back to `curl_cffi`), `numpy`, `Pillow`.
